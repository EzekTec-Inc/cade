# Plugin Development and Lifecycle Guide

CADE plugins extend a running project with manifest-declared tools, skills, and MCP server metadata. The PluginEngine is the canonical source of installed-plugin inventory and lifecycle operations.

## Plugin locations

CADE discovers plugins from these locations:

- **Project scope:** `.cade/plugins/` beneath the current project. These plugins are specific to that project.
- **User scope:** `~/.cade/plugins/`. These plugins are available across projects on the current machine.

The server reports each discovered plugin's scope in the inventory. The current install endpoint installs into the project-local plugin directory. Only project-scoped plugins can be removed from the GUI.

## Package requirements

Installable packages are remote `.tar.gz` archives containing a valid CADE plugin manifest. The manifest declares the plugin's stable identifier, name, version, and any exported capabilities.

Use a stable, URL-safe identifier when installing a package. It is used for lifecycle commands and becomes the directory/key by which the plugin is managed.

## Lifecycle interfaces

All lifecycle interfaces use the server's PluginEngine so that the TUI, GUI, and HTTP API share the same inventory and mutation behavior.

### TUI / REPL

Use the `/plugin` command in a CADE REPL session:

```text
/plugin list
/plugin install <url> <id>
/plugin uninstall <id>
```

- `list` prints the canonical inventory, including the plugin identifier, version, scope, and exported-tool count.
- `install` downloads and installs a package from `url` using `id` as its stable identifier.
- `uninstall` removes a project-local plugin by identifier.

### Web GUI

The **Settings** page includes a **Plugins** section. It:

- loads the canonical plugin inventory;
- refreshes the inventory on demand;
- installs a package from a URL and plugin identifier; and
- exposes **Remove** only for project-scoped plugins.

The GUI refreshes its inventory after a successful install or removal.

### HTTP API

All endpoints are rooted at `/v1`.

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/plugins` | Return the canonical manifest-derived inventory. |
| `POST` | `/plugins/install` | Download and install a plugin package. |
| `DELETE` | `/plugins/{id}` | Remove a project-local plugin. |
| `GET` | `/plugins/events` | Open the Server-Sent Events lifecycle stream. |

Install requests use JSON:

```json
{
  "url": "https://example.invalid/releases/acme-audit.tar.gz",
  "plugin_id": "acme-audit"
}
```

`plugin_id` is optional at the HTTP layer. When omitted, the server derives an identifier from the URL's final path segment. Clients should provide it explicitly to make lifecycle operations predictable.

A successful inventory response contains a `plugins` array and a `count`. Each plugin report includes:

```json
{
  "id": "acme-audit",
  "name": "Acme Audit",
  "version": "1.0.0",
  "scope": "project",
  "status": "active",
  "tools_count": 2,
  "skills_count": 1,
  "mcp_servers_count": 0
}
```

The optional `diagnostic` field is present when the engine has diagnostic information to report.

## Operational behavior

- Inventory is generated by rediscovering manifests from the configured plugin directories; it is not a separate client-side cache.
- Installation and removal refresh the engine's resolved registry before returning.
- Removal of an unknown plugin returns `404`; other lifecycle failures return a structured error response.
- The events endpoint is an SSE connection point. Clients must tolerate future lifecycle event types and should not infer inventory state from a stream connection alone; use `GET /v1/plugins` for the authoritative state.

## Verification checklist

Before distributing or installing a plugin package:

1. Verify the archive URL and plugin identifier.
2. Validate the manifest and all referenced package assets.
3. Install it into a disposable project and confirm it appears in `/plugin list` or the GUI inventory.
4. Exercise each declared capability in that project context.
5. Remove the test installation with `/plugin uninstall <id>` or the GUI, then confirm it no longer appears in the inventory.
