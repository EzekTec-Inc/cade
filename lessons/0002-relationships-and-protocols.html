Lesson 0002 · Milestone 2: Relationships

Relationships, Protocols, and Interaction Semantics

In Lesson 0001, you mastered the rule that elements exist once in the model and are projected into views. Now we look at the arrows connecting them. In system landscapes, ambiguous lines without descriptions or protocols create confusion. Structurizr DSL forces clarity.

1. The Anatomy of a Relationship

Relationships in Structurizr DSL are directional and take up to four parameters: 

sourceIdentifier -> destinationIdentifier [description] [technology] [tags]
  • source -> destination: The direction of intent/invocation (who initiates the call).
  • description: An active verb phrase describing what business function is happening (e.g. "Submits wire transfer requests to").
  • technology (optional): The technical protocol, format, or transport (e.g. "gRPC / TLS", "HTTPS / JSON", "Kafka Topic").
  • tags (optional): Comma-separated labels used for custom styling or filtering (e.g. "Async, Core Banking").

2. Concrete Landscape Example

Notice how each relationship explains both the business intent and the technical conduit: 

workspace "Financial Services Landscape" {
    model {
        customer = person "Retail Customer" "Bank customer with active checking accounts"
        webPortal = softwareSystem "Online Banking Portal" "Customer web application"
        coreBanking = softwareSystem "Core Banking Engine" "Mainframe ledger and transaction engine"
        fraudDetector = softwareSystem "Real-time Fraud Service" "Evaluates transaction risk scores"

        // Directional relationship flows
        customer -> webPortal "Initiates bill payments using" "HTTPS / Browser"
        webPortal -> coreBanking "Executes debit/credit transactions via" "REST / mTLS"
        coreBanking -> fraudDetector "Streams transactions for risk analysis to" "Apache Kafka"
    }

    views {
        systemLandscape "landscape" "Complete end-to-end payment flows" {
            include *
            autoLayout lr
        }
        theme default
    }
}
Architectural Rule of Thumb
Arrows should point in the direction of the dependency/invocation (client → server, publisher → broker), NOT the direction of the return data payload.
