Lesson 0001 · Structurizr DSL Fundamentals

The Core Mental Model: Model vs. Views

Welcome to your first step in Architecture-as-Code. Before writing syntax, we must internalize the single most important principle that separates Structurizr DSL from drawing tools like Visio, Miro, or Draw.io:

The Fundamental Invariant
You do not draw diagrams in Structurizr. You build an underlying semantic model of people, systems, and relationships. Views are simply visual projections filtered and rendered from that single model.

1. The Anatomy of a Workspace

Every Structurizr architecture definition begins with a workspace block containing two mandatory core sections: 

workspace "Enterprise Banking" "High-level architecture landscape" {

    model {
        // 1. Where actors, systems, and relationships are defined
        customer = person "Personal Banking Customer" "A customer with an account"
        bankingApp = softwareSystem "Internet Banking System" "Allows customers to view accounts and make payments"

        customer -> bankingApp "Views account balances and makes payments using" "HTTPS"
    }

    views {
        // 2. Where we choose WHAT to show from the model
        systemLandscape "Overview" "An enterprise overview of our banking landscape" {
            include *
            autoLayout
        }

        theme default
    }
}

2. Key Elements of the Landscape

For System Landscape Architecture, you only need to master two fundamental element types at this stage:

  • person <identifier> <name> [description] [tags]:
    Represents a human user, customer, internal operator, or persona who interacts with your systems.
  • softwareSystem <identifier> <name> [description] [tags]:
    Represents a distinct software system at the highest level of abstraction (e.g. Core Banking System, Fraud Detection Engine, CRM).

3. Connecting Elements (Relationships)

Relationships define unidirectional interactions between two identifiers: 

sourceIdentifier -> destinationIdentifier "Description of interaction" "Technology / Protocol"

Example: customer -> bankingApp "Transfers money using" "JSON/REST"

Knowledge Check: Fluency & Invariant Verification

In Structurizr DSL, if you want to show a software system in three different diagrams (e.g., Landscape, Security, and Operations), how is that achieved?

Correct! Exactly right. The element is declared exactly once inside the model block. Individual views simply project and filter existing elements using expressions like include * or include softwareSystemId.
Not quite. Remember the core rule: the model holds all elements and relationships. Views are only projections. Elements can never be declared inside the views block!
